# Native visual/power connection proof

These tools make fresh isolated profiles with ordinary registered sealed drives,
the real sink/operation/fluid service, and actual LuaRenderObject animations.
The private addon owns tiny64-frame1px stub art solely to exercise API fields.
It is **not** final FX pixel, shader, arc/plume shape or art-installation evidence.

`prepare.py` copies the frozen low-flange flight baseline and exactly the new
`control_legacy_part_002.lua` / `void_fusion_visuals.lua`. It appends only a
read-only observer remote to the private copied `control.lua`. The ordinary
repository control/runtime files are never edited. The observer never calls
Operation.sample, service, register or a setter. Fixture addon initialization
runs after its tech-priests dependency, preserving real initial registration.

`run.py create/test/server/reload` uses the profile as process working directory.
The actual loopback-only server stage is needed because benchmark suppresses
autosaves; it keeps its parent alive, waits for the actual save/completed record
and terminates only its own child. Reload runs from that real autosave.

`verify.py` checks every actual readback RGBA channel against factor/1.5 with
1e-6 float tolerance, exact same operation/sink watts with.01W tolerance,
independent per-drive phases, real fluids, cut/restore, paused plume off while
energy stays powered, sink repair retaining IDs, real save/reload retaining IDs,
and removal/zero remaining sinks/render objects. Operation and visuals must
have identical sample ticks. The observer runs before the nth_tick10 service,
so sample age is explicitly bounded to10ticks. Native working status can change
between that service and the next observation: exact plume gates are checked on
159 stable windows per drive, with all transition witnesses retained separately.
Power/RGBA checks remain strict on all165 samples per drive.

`prepare.py --no-assets` plus `verify_fallback.py` separately proves the optional
animation-name gate: no visual state/objects are created while real draw,
positive fluid stores and native platform motion remain present. Animation
availability uses the installed2.1.24 `helpers.is_valid_animation_path`; no
`prototypes.animation` lookup is invented.

Current isolated evidence is under parent `local-validation/`:

- `thruster-visual-power-native-20261117/visual-power-native-validation.json`
- `thruster-visual-no-assets-native-20261117/optional-visual-fallback-validation.json`

Failed fixture studies/logs remain preserved: an initial observer used runtime-
unavailable table.deepcopy, then was replaced with a plain read-only numeric
copy; initial benchmark-load bookkeeping was corrected to distinguish actual
post-proof reload. No corresponding core/runtime behavior was changed.
